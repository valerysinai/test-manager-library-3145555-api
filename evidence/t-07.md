# Evidencia T-07 · Autenticación con fakes

## Requisitos y alcance

Referencia: HU-01 y HU-02 de ambas versiones de `spec.md`, T-07 de `tasks.md`, artículos II,
IV y IX, `api-contract.md` §§3.1, 3.2, 4 y 5.1 y la adaptación React/Laravel aprobada.

Se implementan dos casos de uso PHP: `LoginService` y `CreateLibrarianService`.
El dominio centraliza la normalización del usuario; los puertos no incluyen tipos de Laravel,
ORM ni biblioteca JWT. No hay nuevos endpoints, columnas, tablas ni cambios de nombres o alcance.

## Escenarios ejecutables

| Criterio | Prueba de aplicación con fakes |
|---|---|
| CA-01.1 | Admin y bibliotecario reciben el resultado de login previsto; el emisor recibe ID, rol e instantes UTC con diferencia exacta de 28.800 segundos |
| CA-01.2 | Usuario ausente y clave incorrecta generan el mismo mensaje genérico; ambos llaman al verificador y ninguno emite token |
| CA-02.1 (nivel aplicación) | Actor bibliotecario recibe `ForbiddenRole` antes de validar entradas o consultar usuarios; actor admin puede crear un bibliotecario |
| CA-01.3 (pendiente) | La prueba del alta no acredita protección de todas las rutas. T-16 debe verificar Bearer ausente/inválido/vencido y 403 por rol en cada endpoint protegido |
| CA-02.2 | Nombre recortado y minúsculo, incluido Unicode; duplicado normalizado rechazado sin sobrescribir ni generar otro hash; conflicto de inserción propagado |
| CA-02.3 | Solicitar admin u otro rol produce `ValidationError` de role; resultado de alta contiene exactamente ID, username y role, sin clave ni hash |
| Validación D-12 | Nombre obligatorio de hasta 120 caracteres, password no vacío; no recorta password ni impone complejidad; altas y logins conservan espacios |
| Reloj C-04 | Cada login toma el instante actual del mismo Clock inyectado; un nuevo login refleja el avance del reloj falso |
| Fallos técnicos | Fallo al generar hash no persiste usuario; fallo al emitir token conserva su error técnico; un token vacío de un adaptador defectuoso no produce un éxito |

Las credenciales de prueba se generan en memoria durante cada escenario. El fake de hash no guarda
contraseñas y no es una implementación criptográfica de producción. El fake de token devuelve un
marcador de prueba sin firma; solo registra ID, rol y fechas. No se versionan credenciales ni hashes
precalculados, ni se registran cuerpos de autenticación.

Las pruebas extienden `PHPUnit\Framework\TestCase`: no arrancan Laravel ni una conexión de datos.
La comprobación inicial de arquitectura recorre también Application y detecta referencias
prohibidas al framework o a adaptadores, incluidos ejemplos introducidos en el test del detector.
Eso no completa la verificación de todas las dependencias ni la composición de T-19.

## Reproducción

```sh
docker build --target test -t manager-library-api:test .
```

Con PHP 8.4 y las dependencias de desarrollo del lockfile instaladas:

```sh
php vendor/bin/phpunit
```
